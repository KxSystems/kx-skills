# KDB.AI sizing skill

Helps size KDB.AI deployments — RAM, disk, and GPU VRAM — from a dataset shape and workload. See [SKILL.md](SKILL.md) for the full workflow Claude follows, and [reference.md](reference.md) for exact byte formulas and the CAGRA VRAM-anchor table.

## What it does
- Starts with discovery: the two hard requirements for a dataset-specific numerical estimate are a volume figure and embedding dimensions. The volume figure is normally current row count, but a user who tracks bytes can give a data-size figure instead — a total size, or a size-per-day plus a retention horizon — and the estimator converts it to rows (labelling a size-derived count as an upper bound). Everything else (index type, update pattern, filters, concurrency) is asked conditionally, and if the volume/dims aren't known it won't invent a number — it'll offer a labelled worked example instead.
- Advises whether to partition the table from KDB.AI's own behaviour — per-table partitioning, and KDB.AI's rule that pruning only helps when the partition column is in the query filter — rather than partitioning by default or importing kdb+/kdb-x thresholds (KDB.AI publishes no row-count threshold and differs from kdb+/kdb-x). It surfaces partitioning when a user wants low memory per query or higher QPS/lower latency — a pruned search touches only the relevant partition, and searches across partitions parallelize — while making clear this shrinks the per-query working set and enables cheap retention, not the sized RAM/disk floor, and is a lever to validate, not a sized throughput number.
- Turns those discovery answers into a shortlist of 2-3 viable index configs (Flat/qFlat, HNSW/qHnsw, IVF-PQ, CAGRA) rather than picking one from row count alone.
- Also derives broad CPU/`NUM_WRK`/`THREADS` starting bands and GPU tier guidance from discovery inputs like active concurrent searches and GPU class — starting points to validate, not final numbers.
- Works in both directions for every hardware dimension (host RAM, GPU VRAM, CPU cores): if the user states what they have, it does a fit check (what fits, and the levers to try when nothing does); if they don't, it sizes what to acquire (host RAM to provision, core band, GPU tier). Modes can mix — e.g. a fixed RAM limit with an open core count.
- Feeds all of the above — rows, dims, vector type, chosen index, workers, and that index's own parameters (`nsplits`/`nbits`, `graph-degree`, etc.) — into a backing script (`estimate.py`) that computes fixed RAM per worker, persisted disk, and CAGRA VRAM from byte-level formulas. This math is validated against real measurements and accurate to within a couple of %.
- Delivers the answer inline in a fixed three-section format: (1) a single recommended starting-configuration block (index, vector type, dims, metric, partition column, top-N, transport, host/KDB.AI cores, `NUM_WRK`/`THREADS`, RAM driver), (2) a short "why this / what to check" reasoning block, and (3) a table of at most three alternative configs each with a "choose this if…" reason. Sizing guidance only — no KDB.AI client-API code (that's the sibling `kdbai` skill's job).

## What it deliberately does not do
It's built to err on the side of caution rather than confidence — no unfounded numbers, no silent defaults, no premature collapse to a single answer:
- Uses your stated numbers verbatim and invents none. Every figure traces to a value you gave, the estimator's output for those values, or a cited doc/measured constant — it won't round or rescale your inputs, won't swap in an example value, and when something wasn't provided it says so rather than guessing.
- Won't invent anything it can't back with a formula or published measurement — no throughput, latency, IOPS, cost, distributed/multi-node topology, or exact CAGRA build peak for a shape that isn't published. Those get pushed to a representative PoC instead.
- Won't guess the use case — unknown update pattern, filters, or query type gets conditional branches (exact vs. HNSW vs. IVF-PQ), not a single pick.
- Won't apply an assumption silently — every default (float32 dtype, a growth multiplier, a provisional efSearch heuristic) is labelled as an assumption, not stated as fact.
- Won't collapse a range to one number under pressure, even when asked directly.
- Doesn't size the sparse/BM25 side of hybrid search — dense side only.
